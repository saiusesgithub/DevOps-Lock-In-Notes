# 8.1 – Testing Terraform Code (Theory)

> **Date:** 07-02-2026

## Why Testing Matters in Terraform

Infrastructure-as-Code (IaC) introduces the same long-term risks as application code. Without testing, Terraform configurations can silently degrade over time, leading to broken deployments, security issues, or unexpected behavior in production.

Testing Terraform code helps ensure:

* Infrastructure behaves as expected
* Changes are safe and intentional
* Drift and misconfigurations are detected early
* Long-term maintainability of infrastructure

This lesson introduces **code rot**, explains how it affects Terraform, and outlines multiple **testing strategies** to prevent it.

---

## Code Rot (Infrastructure Context)

**Code rot** refers to the gradual degradation of a codebase over time due to changes that are not actively managed or validated.

In Terraform and infrastructure, code rot commonly occurs due to:

### 1. Out-of-band changes

Resources are modified manually via cloud provider UI or CLI instead of Terraform.

* Example: Someone edits a security group rule in AWS Console
* Result: Terraform state no longer matches reality (state drift)

### 2. Unpinned provider versions

Providers default to the latest version if not pinned.

* A provider upgrade may introduce breaking changes
* Existing configs may stop working without warning

### 3. Deprecated modules or resource types

* External modules may be deprecated or removed
* Cloud providers may deprecate APIs or resource arguments

### 4. Unapplied Terraform changes

* Config changes applied to staging but not production
* State and config drift apart across environments

Without testing, these issues often go unnoticed until something breaks.

---

## Preventing Code Rot with Testing

Terraform testing is not a single tool or command—it is a **layered approach**.

### Categories of Terraform Testing:

1. Static checks
2. Third-party tooling
3. Manual testing
4. Automated testing

Each layer increases confidence and reduces risk.

---

## 1. Static Checks (Built-in Terraform Tools)

These checks are fast, cheap, and should be run frequently (locally and in CI).

### terraform fmt

* Enforces consistent, opinionated formatting
* Ensures all Terraform files follow the same style
* Prevents style drift across teams

```bash
terraform fmt
```

---

### terraform validate

* Verifies configuration syntax
* Ensures required variables are set
* Checks type correctness (string vs number vs bool)

```bash
terraform validate
```

What it catches:

* Missing required inputs
* Invalid variable types
* Misconfigured resources

---

### terraform plan

* Compares **desired state** (config) with **actual state** (infrastructure)
* Detects drift and unexpected changes

```bash
terraform plan
```

Interpretation:

* **0 changes** → config and infrastructure are in sync
* **Changes detected without config edits** → out-of-band change or drift

Best practice:

* Run `terraform plan` regularly (daily/weekly) even without changes

---

### Custom Validation Rules

Terraform supports custom validation on variables.

* Enforce naming conventions
* Restrict instance sizes
* Validate environment-specific rules

These act as **guardrails inside Terraform itself**.

---

## 2. Third-Party Terraform Testing Tools

These tools provide deeper analysis beyond Terraform core.

### Common Tools

* **tflint**

  * Lints Terraform code
  * Detects unused variables, deprecated syntax

* **checkov**

  * Security and compliance scanning
  * Detects insecure configurations

* **tfsec**

  * Focused on security misconfigurations

* **terrascan**

  * Policy-as-code scanning

* **Terraform Sentinel (Enterprise-only)**

  * Enforces security & compliance rules
  * Available only with Terraform Cloud Enterprise

These tools are typically run in CI pipelines.

---

## 3. Manual Testing

The classic Terraform workflow:

```text
terraform init
terraform plan
terraform apply
terraform destroy
```

Manual testing answers:

* Does the infrastructure actually deploy?
* Does the application respond correctly?

Limitations:

* Slow
* Error-prone
* Not scalable

Manual testing is useful early but should not be the long-term strategy.

---

## 4. Automated Testing

Manual workflows can and should be automated.

### Simple Automation (Shell Scripts)

Example approach:

1. Initialize Terraform
2. Apply infrastructure
3. Wait for resources
4. Make HTTP/API calls to validate behavior
5. Destroy infrastructure

This can be run in CI for basic validation.

Pros:

* Simple
* Easy to implement

Cons:

* Limited assertions
* Hard to scale

---

### Advanced Automation with TerraTest

**TerraTest** is a Go-based testing framework for Terraform.

Capabilities:

* Programmatic control of Terraform lifecycle
* Retry logic with timeouts
* Assertions on infrastructure behavior
* Guaranteed cleanup using deferred destroy

Conceptual flow:

1. Initialize Terraform
2. Apply configuration
3. Query outputs (IP, DNS, etc.)
4. Make assertions (HTTP responses, ports, metadata)
5. Destroy resources regardless of test outcome

Key benefit:

* Infrastructure testing becomes **real software testing**

---

## Key Takeaways

* Infrastructure code **rots** just like application code
* Testing is the primary defense against drift and breakage
* Terraform testing should be **layered**, not single-tool
* Start with built-in commands, expand to security tooling
* Automate wherever possible
* For complex systems, use TerraTest for real assertions

Terraform testing is no longer optional—it is a core skill for modern DevOps and Platform Engineering.
