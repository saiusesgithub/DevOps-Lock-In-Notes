# 8.2 – Testing Terraform Code (Practice)

> **Date:** 07-02-2026

This section demonstrates **practical testing techniques** for Terraform code. It builds directly on the testing theory (8.1) and shows how to structure a repository and implement multiple levels of testing—from static checks to full end‑to‑end infrastructure tests.

---

## Recommended Repository Layout

A clean repo structure makes testing, onboarding, and maintenance much easier.

```
/modules    -> Custom Terraform modules you build
/examples   -> Working examples that consume modules
/deployed   -> Real environments (prod, staging, etc.)
/test       -> All tests and validation logic
```

### Purpose of Each Directory

* **modules/**
  Contains reusable Terraform modules. In this demo, a simple *hello‑world* module is used instead of the larger web app.

* **examples/**
  Shows how to consume the module in a real configuration. This is what tests will deploy.

* **deployed/**
  Intended for actual environments (prod, staging, dev). Empty here, but this is where real deployments live.

* **test/**
  Contains all testing logic: static checks, Bash tests, and Terratest.

---

## Hello‑World Module (What We Are Testing)

The module under test contains:

* An **EC2 instance**
* A **security group** allowing inbound traffic on port **8080**
* A **user_data** script that runs a basic web server

This module is intentionally simple so testing concepts are easy to understand.

---

## Example Configuration (examples/)

The examples directory demonstrates how to consume the module:

* Backend and provider configuration
* Module referenced via **relative path**
* Outputs exposed:

  * Instance IP address
  * URL built from that IP (used for testing)

These outputs allow tests to verify that the infrastructure is actually running and reachable.

## Static Checks (Lightweight Validation)

These checks do not provision infrastructure, but they catch many issues early.

### terraform fmt

Ensures consistent formatting using Terraform’s built‑in style guide.

* `terraform fmt` → auto‑formats files
* `terraform fmt -check` → fails if formatting is incorrect

Ideal for **CI enforcement** so all contributors follow the same style.

---

### terraform validate

Checks:

* Required variables are provided
* Types match (string vs number vs bool)
* Configuration is syntactically valid

Does **not** contact cloud providers.

---

### terraform plan

Compares desired configuration with actual deployed state.

* Detects **out‑of‑band changes**
* Useful as a **periodic CI check**

If `terraform plan` shows changes but no config was updated → something drifted.

---

### Custom Validation Rules

Terraform allows validation inside variable blocks.

Example use cases:

* Enforce password length
* Restrict allowed instance types
* Validate naming conventions

These rules are evaluated during `terraform plan`.

---

### Third‑Party Static Tools

Additional scanners can analyze Terraform code for:

* Security issues
* Best‑practice violations
* Compliance problems

Examples:

* tflint
* tfsec
* checkov
* terrascan

## Bash Script Testing (Simple End‑to‑End Test)

A basic but effective way to test infrastructure is a Bash script that:

1. Initializes Terraform
2. Applies the example configuration
3. Waits for the instance to boot
4. Sends an HTTP request
5. Destroys the infrastructure

### Bash Test Flow

```
cd examples/hello-world
terraform init
terraform apply -auto-approve
sleep 60
curl http://<INSTANCE_IP>:8080
terraform destroy -auto-approve
```

### Characteristics

* ✔ Easy to understand
* ✔ Good for small projects
* ❌ Uses fixed sleep (not robust)
* ❌ Limited assertions

If the curl command fails, the script exits with a non‑zero code, causing CI to fail.

## Terratest (Robust Infrastructure Testing)

For production‑grade testing, Terraform can be tested using **Go** via the **Terratest** framework from Gruntwork.

### Why Terratest?

* Retry logic instead of fixed sleeps
* Strong assertions
* Uses real programming constructs
* Automatic cleanup via `defer`

---

### Terratest Flow

1. Initialize Terraform
2. Apply configuration
3. Read Terraform outputs
4. Retry HTTP requests until success
5. Destroy infrastructure (even on failure)

---

### Terratest Example (Go)

```go
func TestTerraformHelloWorldExample(t *testing.T) {
  terraformOptions := terraform.WithDefaultRetryableErrors(t, &terraform.Options{
    TerraformDir: "../../examples/hello-world",
  })

  defer terraform.Destroy(t, terraformOptions)

  terraform.InitAndApply(t, terraformOptions)

  instanceURL := terraform.Output(t, terraformOptions, "url")

  maxRetries := 30
  timeBetweenRetries := 10 * time.Second

  http_helper.HttpGetWithRetry(
    t,
    instanceURL,
    nil,
    maxRetries,
    timeBetweenRetries,
    func(status int, body string) bool {
      return status == 200
    },
  )
}
```

### Key Advantages

* No arbitrary sleep times
* Controlled retry behavior
* Automatic cleanup
* CI‑friendly

## Periodic Terraform Plan in CI

A highly effective test is to **periodically run terraform plan** in CI/CD.

Purpose:

* Detect UI or manual changes
* Catch drift early
* Enforce IaC discipline

If a plan shows changes unexpectedly:

* Either revert them
* Or codify them in Terraform
