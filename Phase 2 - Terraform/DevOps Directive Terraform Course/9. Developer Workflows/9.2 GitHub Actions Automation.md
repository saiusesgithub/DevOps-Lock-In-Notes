# 9.2 – Automating Terraform Deployment with GitHub Actions

> **Date:** 07-02-2026

This section demonstrates how to fully automate Terraform workflows using **GitHub Actions**, tying together everything learned so far: environments, testing, CI/CD, and safe deployments.

---

## Purpose of Automation

At this stage, Terraform usage moves from **manual CLI-driven workflows** to **event-driven automation**. The goal is to:

* Remove human error from `terraform apply`
* Ensure infrastructure changes are reviewed and tested
* Deploy consistently across **staging** and **production**
* Use GitHub as the single source of truth

Automation is triggered by **GitHub events**, not people running commands locally.

---

## Workflow Triggers (GitHub Events)

The GitHub Actions workflow responds to **three events**:

1. **Push to `main` branch**
   → Deploys **staging** environment

2. **Release created (`vX.Y.Z`)**
   → Deploys **production** environment

3. **Pull Request opened**
   → Runs **Terraform plan + tests only** (no deploy)

```yaml
on:
  push:
    branches:
      - main
  release:
    types: [published]
  pull_request:
```

This separation ensures:

* No accidental production deploys
* Every change is tested before merge
* Production deploys are intentional and auditable

---

## High-Level Workflow Logic

The automated pipeline performs the following steps:

1. Checkout repository
2. Install a **specific Terraform version**
3. Run static checks (`terraform fmt`)
4. Initialize Terraform
5. Run `terraform plan` (PRs only)
6. Post plan output as a PR comment
7. Run **Terratest** on PRs
8. Detect target environment (staging / production)
9. Apply **global infrastructure** (DNS, shared resources)
10. Apply **environment-specific configuration**

Each step is conditional based on the triggering event.

---

## GitHub Actions Job Structure

* Single job: `terraform`
* Runs on `ubuntu-latest`
* Uses **GitHub Secrets** for credentials

```yaml
env:
  AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
  AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
```

These secrets correspond to an IAM user with sufficient permissions.

> ⚠️ Note: This demo uses **long‑lived credentials**. In production, **OIDC with short‑lived credentials** is strongly recommended.

---

## Working Directory Strategy

Terraform commands are executed from a **default working directory**, pointing to the staging configuration:

```yaml
defaults:
  run:
    working-directory: 07-managing-multiple-environments/file-structure/staging
```

This avoids repeating paths across steps and ensures consistency.

## Static Checks (Fail Fast)

### Terraform Format

```bash
terraform fmt -check
```

* Enforces consistent formatting
* Fails the workflow if formatting is incorrect
* Ideal for CI enforcement

### Terraform Init

```bash
terraform init
```

* Always required before plan/apply
* Downloads providers and configures backend

---

## Pull Request Behavior (Safe Mode)

When `github.event_name == 'pull_request'`:

### Terraform Plan

* Runs `terraform plan`
* Uses `-no-color` for clean CI logs
* Continues on error so output can be captured

### Plan Output as PR Comment

A GitHub Script step:

* Collects plan output
* Posts it directly on the PR
* Shows:

  * Format status
  * Init status
  * Plan status
  * Full plan details (collapsible)

This gives reviewers **full visibility** into infrastructure changes.

### Plan Failure Handling

If the plan fails:

* Workflow **fails explicitly** after posting output
* Prevents merging broken infrastructure

---

## Infrastructure Testing on PRs

### Terratest Setup

* Go is installed via `actions/setup-go`
* Tests run only on pull requests

```bash
go test . -v -timeout 10m
```

Terratest:

* Provisions real infrastructure
* Performs HTTP checks
* Automatically destroys resources via `defer terraform.Destroy`

This ensures:

* Infrastructure actually works
* No orphaned cloud resources

---

## Environment Detection Logic

A shell step inspects the Git ref:

* `refs/heads/main` → **staging**
* `refs/tags/vX.Y.Z` → **production**
* Anything else → **unknown**

This output controls which apply steps run next.

---

## Applying Infrastructure

### Global Configuration

Applied for **both staging and production**:

* Shared resources (e.g., Route 53 zone)
* Executed before environment-specific applies

### Staging Apply

Triggered by:

* Push to `main`

```bash
terraform apply -auto-approve
```

### Production Apply

Triggered by:

* Release creation (`vX.Y.Z`)

Runs from the production directory with its own backend and state.

## End-to-End Demo Summary

The demo validates all three workflows:

1. **Push to main**

   * Deploys global + staging infrastructure

2. **Create release**

   * Deploys global + production infrastructure

3. **Open pull request**

   * Runs plan
   * Posts plan to PR
   * Executes Terratest
   * Skips all applies

## Cost & Safety Considerations

* Infrastructure is **not auto-destroyed** after demo
* Manual `terraform destroy` is required
* Triggers can be commented out to prevent accidental redeploys

This highlights an important real-world practice:

> **Always control when automation is enabled.**

---

## Key Takeaways

* Terraform should never be applied manually in mature setups
* GitHub Actions provides:

  * Safety
  * Auditability
  * Repeatability
* Separate workflows for PRs, staging, and production are essential
* Testing infrastructure is just as important as testing code

This section completes the transition from **learning Terraform** to **operating Terraform professionally**.
