## Using Local Variables (Recap in Practice)

Local variables:

* Are **scoped to the project**
* Cannot be overridden at runtime
* Reduce duplication

Used when:

* A value repeats across resources
* A value may change later

Example:

```
locals {
  example_variable = "example_value"
}
```

Think of locals as **constants inside your Terraform project**.

## Input Variables in Practice

In the example configuration:

* EC2 instance
* Database instance

Previously hardcoded values are now replaced with **input variables**.

### Why `variables.tf`?

Variables:

* Can be defined anywhere
* Are pulled into a **dedicated file** for clarity

This gives:

* A single place to see what is configurable
* Cleaner `main.tf`

---

## Example Input Variables

```
variable "ami" {
  description = "Amazon machine image to use for ec2 instance"
  type        = string
  default     = "ami-011899242bb902164" # Ubuntu 20.04 LTS // us-east-1
}

variable "instance_type" {
  description = "ec2 instance type"
  type        = string
  default     = "t2.micro"
}
```

These variables can now be referenced using:

```
var.ami
var.instance_type
```

---

## Referencing Variables Inside Resources

```
resource "aws_instance" "instance_1" {
  ami             = var.ami
  instance_type   = var.instance_type
  security_groups = [aws_security_group.instances.name]
  user_data       = <<-EOF
              #!/bin/bash
              echo "Hello, World 1" > index.html
              python3 -m http.server 8080 &
              EOF
}
```

This removes hardcoding and allows runtime customization.

## tfvars Files — Supplying Variable Values

Non-sensitive values are stored in `terraform.tfvars`:

```
bucket_prefix = "devops-directive-web-app-data"
domain        = "devopsdeployed.com"
db_name       = "mydb"
db_user       = "foo"
# db_pass intentionally omitted
```

### Key Notes

* `terraform.tfvars` is **auto-loaded**
* Other `.tfvars` files must be passed explicitly

Example:

```
terraform apply -var-file=staging.tfvars
```

---

## Handling Sensitive Variables

Sensitive data (e.g., DB passwords):

* Should **NOT** be stored in `.tfvars`
* Should be passed at runtime or via secret managers

Example variable:

```
variable "db_pass" {
  type      = string
  sensitive = true
}
```

Terraform will mask this value in output and plans.

---

## Passing Variables at Runtime

```
terraform apply \
  -var "db_user=myuser" \
  -var "db_pass=something_super_secure"
```

This method:

* Has **highest precedence**
* Is ideal for CI/CD pipelines

---

## Outputs — Exposing Runtime Values

Outputs are added to expose values after deployment:

```
output "instance_1_ip_addr" {
  value = aws_instance.instance_1.public_ip
}
```

Example output:

```
db_instance_addr = "terraform-20210504182745335900000001.cr2ub9wmsmpg.us-east-1.rds.amazonaws.com"
instance_ip_addr = "172.31.24.95"
```

Available via:

* After `terraform apply`
* `terraform output`

## Applying Variables to the Web App Architecture

The web app configuration is refactored using variables for:

* AWS region
* AMI
* EC2 instance type
* S3 bucket name
* Route 53 domain
* Database name

## Environment-Based Deployments

With variables in place, we can now support:

* `dev.tfvars`
* `staging.tfvars`

## Execution Flow (Unchanged)

The workflow remains the same:

```
terraform init

```

The difference:

* Outputs are printed
* Behavior depends on variable values

## Key Takeaways

* Variables remove hardcoding
* tfvars separate config from logic
* Sensitive data must stay out of repos
* Outputs enable composition and automation

## Variable files
`variables.tfvars` (or `<FILENAME>.auto.tfvars`) automatically applied 

## Apply default
`terraform apply`

## Apply a different variable file
`terraform apply -var-file=another-variable-file.tfvars`

## Passing Variable via Prompt
If value not specified, Terraform will prompt for value. (this is okay for testing... but don't depend on it since you should be automating things!)
```
  var.db_pass
  password for database

  Enter a value:
```

## Passing Variables via CLI
`terraform apply -var="db_pass=$DB_PASS_ENV_VAR"`
