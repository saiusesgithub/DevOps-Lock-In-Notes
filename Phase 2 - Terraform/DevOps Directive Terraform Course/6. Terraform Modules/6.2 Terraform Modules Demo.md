# Part 6.2 — Using Terraform Modules in Practice

> **Objective:** Learn how to (1) consume third‑party Terraform modules and (2) refactor an existing Terraform project into reusable, composable modules that can be instantiated multiple times.

> **Date:** 07-02-2026

---

## Overview of This Section

Now that we understand **how Terraform modules work**, this demo focuses on **practical usage**:

1. Consuming a **third‑party module** from the Terraform Registry
2. Refactoring our existing **web application infrastructure** into a reusable module
3. Deploying **multiple copies** of that module with different configurations

This section is where Terraform truly starts to scale.

---

## Part 1 — Consuming a Third‑Party Module (Consul)

### Why Third‑Party Modules Matter

Some systems are **complex by nature**:

* Many resources
* Deep provider knowledge required
* Best practices baked in

Rather than rebuilding these systems from scratch, Terraform allows us to **consume community or vendor‑maintained modules**.

In this example, we deploy **Consul**, a HashiCorp tool for service discovery and networking automation.

---

## Consul Module (High Level)

* Published and maintained by HashiCorp
* Available via the **Terraform Registry**
* Provisions **dozens of resources** behind the scenes
* Exposes only **important, configurable inputs**

By using this module, we:

* Avoid manual complexity
* Inherit best practices
* Focus only on required inputs

---

## Consul Module — main.tf

```hcl
terraform {
  backend "s3" {
    bucket         = "devops-directive-tf-state"
    key            = "06-organization-and-modules/consul/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-locking"
    encrypt        = true
  }

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

############################################################
## Consul Third‑Party Module
## Repo: https://github.com/hashicorp/terraform-aws-consul
############################################################
module "consul" {
  source = "git@github.com:hashicorp/terraform-aws-consul.git"
}
```

### What Happens When You Run This?

```bash
terraform init
terraform plan
```

Terraform shows that **~52 AWS resources** will be provisioned, including:

* EC2 instances
* IAM roles and policies
* Networking resources
* Security groups

All of this complexity is abstracted away.

## Part 2 — Refactoring the Web Application Into a Module

### Why Refactor?

Our earlier configuration:

* Was correct
* Worked end‑to‑end
* But was **hard to read, reuse, and scale**

The goal now is to:

* Break the system into logical components
* Parameterize it with variables
* Turn it into a reusable **web‑app module**

---

## New Project Structure

```text
06-organization-and-modules
├── README.md
├── web-app
│   └── main.tf          # consumes the module
└── web-app-module
    ├── compute.tf
    ├── database.tf
    ├── dns.tf
    ├── networking.tf
    ├── storage.tf
    ├── outputs.tf
    ├── variables.tf
    └── main.tf
```

### Key Idea

* `web-app-module` → **child module** (reusable)
* `web-app` → **root module** (consumer)

---

## web-app-module — main.tf

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
  }
}
```

Each `.tf` file now owns a **single concern**:

* `compute.tf` → EC2
* `database.tf` → RDS
* `storage.tf` → S3
* `networking.tf` → ALB, SGs
* `dns.tf` → Route 53

---

## web-app-module — variables.tf

```hcl
variable "app_name" { type = string }
variable "environment_name" { type = string }
variable "bucket_prefix" { type = string }
variable "domain" { type = string }
variable "instance_type" { type = string }
variable "db_name" { type = string }
variable "db_user" { type = string }
variable "db_pass" {
  type      = string
  sensitive = true
}
variable "create_dns_zone" {
  type    = bool
  default = true
}
```

These variables allow the same module to be reused across:

* dev
* staging
* production

## Consuming the Web App Module

Now we consume the module **twice** from a root configuration.

### web-app/main.tf

```hcl
terraform {
  backend "s3" {
    bucket         = "devops-directive-tf-state"
    key            = "06-organization-and-modules/web-app/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-locking"
    encrypt        = true
  }

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}
```

---

## Sensitive Variables (Root Module)

```hcl
variable "db_pass_1" {
  type      = string
  sensitive = true
}

variable "db_pass_2" {
  type      = string
  sensitive = true
}
```

Passwords are **not stored in code**.

---

## Module Instance #1

```hcl
module "web_app_1" {
  source = "../web-app-module"

  bucket_prefix    = "web-app-1-data"
  domain           = "devopsdeployed.com"
  app_name         = "web-app-1"
  environment_name = "production"
  instance_type    = "t2.micro"
  create_dns_zone  = true
  db_name          = "webapp1db"
  db_user          = "foo"
  db_pass          = var.db_pass_1
}
```

---

## Module Instance #2

```hcl
module "web_app_2" {
  source = "../web-app-module"

  bucket_prefix    = "web-app-2-data"
  domain           = "anotherdevopsdeployed.com"
  app_name         = "web-app-2"
  environment_name = "production"
  instance_type    = "t2.micro"
  create_dns_zone  = true
  db_name          = "webapp2db"
  db_user          = "bar"
  db_pass          = var.db_pass_2
}
```

---

## Applying the Configuration

```bash
terraform init
terraform apply
```

Terraform prompts for:

* `db_pass_1`
* `db_pass_2`

After apply completes:

* 2 web apps
* 4 EC2 instances
* 2 databases
* 2 load balancers
* 2 S3 buckets

All created from **one reusable module**.

## Key Takeaways

* Third‑party modules save massive effort
* Modules enable true reuse
* Variables differentiate environments
* Sensitive data stays out of code
* One module → many deployments

Terraform modules turn infrastructure from **scripts** into **platforms**.
