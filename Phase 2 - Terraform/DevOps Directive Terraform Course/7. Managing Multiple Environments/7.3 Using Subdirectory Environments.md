# 7.3 – Managing Multiple Environments Using Subdirectories

> **Date:** 07-02-2026

## Context

After destroying the environments created using Terraform workspaces, this section demonstrates an **alternative approach** to managing multiple environments using **directory structure** within the filesystem.

Instead of a single configuration with multiple workspaces, each environment is represented explicitly as its own directory.

---

## Directory Layout

The project is structured into three main subdirectories:

```
.
├── global/
│   └── main.tf
├── production/
│   └── main.tf
└── staging/
    └── main.tf
```

### Purpose of Each Directory

* **global/**

  * Contains resources shared across environments
  * Example: Route 53 Hosted Zone

* **production/**

  * Production-specific deployment
  * Consumes shared global resources

* **staging/**

  * Staging-specific deployment
  * Also consumes shared global resources

---

## Global Configuration

The `global` directory is used for infrastructure that should exist **once** and be shared across environments.

In this example, that shared resource is the **Route 53 Hosted Zone**.

### global/main.tf

```hcl
terraform {
  backend "s3" {
    bucket         = "devops-directive-tf-state"
    key            = "07-managing-multiple-environments/global/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-locking"
    encrypt        = true
  }

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_route53_zone" "primary" {
  name = "devopsdeploy.com"
}
```

### Deployment Order

1. Navigate to `global/`
2. Run:

   ```
   terraform init
   terraform apply
   ```
3. This creates the shared DNS zone used by all environments

---

## Production and Staging Configurations

Both `production` and `staging` directories deploy the web application module.

The **key difference from the workspace approach** is:

* `create_dns_zone = false`
* DNS is assumed to already exist (created by `global`)

### production/main.tf (example)

```hcl
module "web_app" {
  source = "../../06-organization-and-modules/web-app-module"

  bucket_prefix    = "web-app-production"
  domain           = "devopsdeploy.com"
  environment_name = "production"
  instance_type    = "t2.micro"
  create_dns_zone  = false
  db_name          = "productiondb"
  db_user          = "foo"
  db_pass          = var.db_pass
}
```

### staging/main.tf (example)

```hcl
module "web_app" {
  source = "../../06-organization-and-modules/web-app-module"

  bucket_prefix    = "web-app-staging"
  domain           = "devopsdeploy.com"
  environment_name = "staging"
  instance_type    = "t2.micro"
  create_dns_zone  = false
  db_name          = "stagingdb"
  db_user          = "foo"
  db_pass          = var.db_pass
}
```

Each environment is deployed independently by navigating into its directory and running:

```
terraform init
terraform apply
```

---

## Why This Approach Works Well

### Advantages

* File structure clearly represents deployed infrastructure
* Easier to reason about environments by just browsing the repo
* Separate backends per environment → better security isolation
* Lower risk of applying changes to the wrong environment

### Disadvantages

* Some code duplication between environment directories
* Backend configuration values must be hardcoded
* Requires navigating into each directory to apply changes

---

## Comparison with Workspaces

| Aspect            | Workspaces       | Subdirectories    |
| ----------------- | ---------------- | ----------------- |
| Visibility        | Low (CLI needed) | High (filesystem) |
| Safety            | Risky if manual  | Safer by design   |
| Backend isolation | Shared           | Fully isolated    |
| Code duplication  | Minimal          | Higher            |

---

## Final Takeaway

The subdirectory-based approach makes the **codebase itself a representation of reality**.

Although it introduces some duplication, it improves clarity, security, and safety—especially when combined with automation tools like Terragrunt.

Both approaches are valid, but this method scales better for larger teams and production systems.
