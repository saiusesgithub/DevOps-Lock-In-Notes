# Part 7.1 — Managing Multiple Environments with Terraform

> **Objective:** Learn how to deploy and manage multiple environments (dev, staging, prod) using Terraform, and understand the trade-offs between the two most common approaches.

> **Date:** 07-02-2026

---

## Why Multiple Environments Matter

So far, we’ve:

* Built a complete web application infrastructure
* Modularized it using Terraform modules
* Learned how to reuse and parameterize configurations

In real-world systems, **one environment is never enough**.

Typically, you’ll want:

* **Development** → fast iteration, frequent changes
* **Staging** → production-like testing
* **Production** → stable, controlled changes

The goal is to:

* Keep environments **as similar as possible**
* Change **only what’s necessary** (scale, names, credentials, limits)

Terraform supports this in **two primary ways**:

1. Terraform Workspaces
2. Separate Environment Directories

## Approach 1 — Terraform Workspaces

![alt text](Images\terraform-workspaces.png)

Terraform workspaces allow you to manage **multiple state files** within a **single backend**.

Each workspace represents a separate environment.

Example:

* `default`
* `dev`
* `staging`
* `prod`

All share the **same Terraform configuration**, but have **separate state**.

### How It Works

* One codebase
* One backend (S3 or Terraform Cloud)
* Multiple named state files

You switch environments using:

```
terraform workspace select dev
terraform apply
```

### terraform.workspace Expression

Terraform exposes the active workspace via:

```
terraform.workspace
```

This can be used to dynamically name resources:

* `myapp-dev-db`
* `myapp-staging-db`
* `myapp-prod-db`

---

## Pros of Workspaces

* Very easy to get started
* Minimal code duplication
* Single configuration deployed multiple times
* Convenient dynamic naming using `terraform.workspace`

---

## Cons of Workspaces

⚠️ **Human Error Risk**

* Easy to forget which workspace is active
* Applying a change in the wrong workspace can impact production

⚠️ **Shared Backend**

* All environments live in the same backend
* Hard to isolate permissions
* Anyone with backend access usually sees all environments

⚠️ **Reduced Visibility**

* Code alone does not show which environments exist
* You must run Terraform commands to discover deployed states

Workspaces are **much safer when fully automated**, but risky when used manually.

---

## Approach 2 — Separate Environment Directories

![alt text](Images\terraform-sub-directories.png)

Instead of workspaces, you create **separate directories** per environment.

Example structure:

```
modules/
  web-app/

environments/
  dev/
  staging/
  production/
```

Each environment:

* Has its own backend
* Has its own variables
* Explicitly represents deployed state

---

## Pros of Separate Directories

✅ **Backend Isolation**

* Separate S3 buckets / state files
* Different permissions per environment
* Strong security boundaries

✅ **Reduced Human Error**

* You must intentionally enter the environment directory
* Harder to accidentally modify prod

✅ **Clear Code Representation**

* Codebase shows exactly what is deployed
* Easy to audit configurations

---

## Cons of Separate Directories

❌ **More Code Duplication**

* Each environment has a similar `main.tf`
* Risk of configs drifting apart

❌ **Operational Overhead**

* Must run Terraform separately per environment
* Requires navigation between directories

This trade-off is usually acceptable for **medium to large systems**.

---

## Scaling Beyond a Single Terraform Project

As infrastructure grows, a single massive Terraform project becomes unmanageable.

Instead, teams often split by **change frequency** or **responsibility**:

Examples:

* Networking (VPC, subnets)
* Compute (EC2, autoscaling)
* Databases
* Shared services

Each component can be:

* A separate Terraform project
* With its own backend

---

## Terraform Remote State

Terraform allows one configuration to **read outputs from another** using **remote state**.

This enables:

* Isolated projects
* Shared infrastructure data
* Clean dependency boundaries

Example use case:

* Networking project outputs subnet IDs
* Compute project reads those outputs

This avoids merging everything into one repo.

---

## Managing Complexity — Terragrunt

As environments and projects multiply, Terraform alone can become verbose.

**Terragrunt** (by Gruntwork) helps by:

* Reducing duplication
* Managing backend configs
* Automating multi-environment workflows
* Supporting multi-account setups

Terragrunt is especially useful when:

* You have many environments
* You use multiple cloud accounts
* You want strict DRY (Don’t Repeat Yourself)

---

## Summary: Choosing an Approach

| Approach    | Best For                               | Risk        |
| ----------- | -------------------------------------- | ----------- |
| Workspaces  | Small projects, automation-first teams | Human error |
| Directories | Medium–large systems, strong isolation | Duplication |

There is **no single correct answer**.

Your choice depends on:

* Team size
* Automation maturity
* Security requirements
* Infrastructure complexity

---

## Key Takeaways

* Multiple environments are mandatory in real systems
* Workspaces are convenient but risky when manual
* Separate directories offer clarity and isolation
* Remote state enables clean cross-project dependencies
* Terragrunt helps manage large-scale complexity
