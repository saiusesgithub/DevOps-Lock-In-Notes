# Part 7.2 — Managing Multiple Environments with Terraform (Workspaces Demo)

> **Objective:** Demonstrate how Terraform Workspaces can be used in practice to deploy the *same infrastructure code* into multiple isolated environments (production, staging) using a shared backend.

> **Date:** 07-02-2026

## Context

In **Part 7.1**, we discussed two main approaches for managing multiple environments:

1. **Terraform Workspaces**
2. **Separate Directory Structures**

In this section, we implement the **workspaces-based approach** end-to-end using our modularized web application.

---

## Workspace-Based Environment Management

Terraform Workspaces allow you to store **multiple state files** inside the **same remote backend**, separated by workspace name.

Each workspace represents a different environment:

* `production`
* `staging`
* `default` (initial workspace)

Terraform exposes the active workspace name via:

```
terraform.workspace
```

This enables us to dynamically change resource names and behavior based on the environment.

## Backend & Provider Configuration

As always, we begin by configuring the backend and provider.

```
terraform {
  backend "s3" {
    bucket         = "devops-directive-tf-state"
    key            = "07-managing-multiple-environments/workspaces/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-locking"
    encrypt        = true
  }

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}
```

---

## Sensitive Input Variable

We define the database password as a sensitive input variable.

```
variable "db_pass" {
  description = "password for database"
  type        = string
  sensitive   = true
}
```

This value will be passed at runtime rather than stored in files.

---

## Using the Workspace Name

We store the current workspace name in a local variable for reuse.

```
locals {
  environment_name = terraform.workspace
}
```

This allows us to:

* Avoid naming collisions
* Apply environment-specific logic

---

## Avoiding Global Resource Conflicts

Some AWS resources (like **S3 buckets**) are globally scoped.

To avoid conflicts, we postfix names with the environment:

```
resource "aws_s3_bucket" "bucket" {
  bucket = "web-app-data-${local.environment_name}"
}
```

---

## Consuming the Web App Module

We now consume the previously created **web application module**.

```
module "web_app" {
  source = "../../06-organization-and-modules/web-app-module"

  bucket_prefix    = "web-app-data-${local.environment_name}"
  domain           = "devopsdeployed.com"
  environment_name = local.environment_name
  instance_type    = "t2.micro"

  create_dns_zone  = terraform.workspace == "production" ? true : false

  db_name = "${local.environment_name}mydb"
  db_user = "foo"
  db_pass = var.db_pass
}
```

### Key Concepts Used Here

* **Workspace-aware naming**
* **Conditionals** for global resources
* **Variables passed through modules**

---

## Conditional DNS Zone Logic

DNS zones are global and should be created only once.

* **Production** → create Route 53 hosted zone
* **Staging / Dev** → reuse existing zone

This is controlled using a boolean variable inside the module:

```
create_dns_zone = terraform.workspace == "production" ? true : false
```

Inside the module:

* `count = 1` → create resource
* `count = 0` → skip resource

The inverse logic is applied to a `data` block to look up an existing zone.

---

## Subdomain Logic

Production uses the root domain:

```
devopsdeployed.com
```

Other environments use subdomains:

```
staging.devopsdeployed.com
```

This is handled via locals and conditionals inside the module.

---

## Creating Environments with Workspaces

### Initialize Terraform

```
terraform init
```

### Create Production Workspace

```
terraform workspace new production
terraform workspace list
```

Apply:

```
terraform apply
```

Terraform will prompt for the database password.

---

### Create Staging Workspace

```
terraform workspace new staging
terraform workspace list
terraform apply
```

Result:

* Production → `devopsdeployed.com`
* Staging → `staging.devopsdeployed.com`

Both environments are:

* Fully isolated
* Created from the same codebase
* Stored as separate state files

---

## Cleanup

Destroy environments **one workspace at a time**:

```
terraform workspace select production
terraform destroy

terraform workspace select staging
terraform destroy
```

---

## Key Takeaways

* Terraform Workspaces enable multi-environment deployments from one codebase
* `terraform.workspace` allows dynamic configuration
* Conditionals help manage global vs environment-scoped resources
* Workspaces are powerful but require discipline to avoid mistakes
