---

# 🧠 Core Concept: The `GITHUB_TOKEN`

Every GitHub Actions workflow automatically receives a token:

```
secrets.GITHUB_TOKEN
```

This token:

* Is generated automatically by GitHub
* Is scoped to the repository
* Is short-lived (valid only for the workflow run)
* Is used to authenticate API operations

Examples of what it can do:

* Read repository contents
* Interact with pull requests
* Create issues
* Push commits (if permitted)
* Publish packages

---

# 🔐 Default Permission Model

By default, the `GITHUB_TOKEN` has:

* `contents: read`
* `packages: read`
* Everything else → `none`

Meaning:

* You can checkout the repository
* You can read packages
* You cannot modify pull requests, issues, releases, etc.

Unless you explicitly grant permission.

---

# ⚙️ The `permissions:` Block

You control token access using the `permissions:` key.

It can be defined:

* At the workflow level
* Or at the job level (more granular control)

Syntax:

```yaml
permissions:
  pull-requests: read
```

Possible values:

* `read`
* `write`
* `none`

This applies to various resource types:

* contents
* pull-requests
* issues
* checks
* deployments
* packages
* actions
* discussions
* and more

# 🧪 Demonstration Workflow — Read vs Write

## 🟡 Job 1 — Read-Only Pull Request Access

```yaml
read-only-pr:
  runs-on: ubuntu-24.04
  permissions:
    pull-requests: read
```

### What Happens?

Step 1 — List Pull Requests (allowed)

```bash
gh pr list --limit 5
```

✅ This works because listing PRs requires read access.

Step 2 — Attempt to Modify PR (expected to fail)

```bash
gh pr edit 1 --add-label "documentation"
```

❌ This fails.

Why?

Because modifying a PR requires `write` permission.

Error shown:

```
Resource not accessible by integration
```

This confirms the token is properly restricted.

---

## 🟢 Job 2 — Write Pull Request Access

```yaml
read-write-pr:
  runs-on: ubuntu-24.04
  permissions:
    pull-requests: write
```

Now the same command succeeds:

```bash
gh pr edit 1 --add-label "documentation"
```

✅ Label gets applied successfully.

# 🔄 Why `GH_TOKEN` Is Needed

The GitHub CLI (`gh`) expects authentication via:

```
GH_TOKEN
```

So we map the automatically provided token:

```yaml
env:
  GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

This allows `gh` CLI commands to authenticate properly.

---

# 🛡️ Security Best Practice — Least Privilege

You should always:

* Grant the minimum permissions required
* Avoid `write` access unless necessary
* Restrict permissions at job level when possible

Example philosophy:

* Build jobs → only need `contents: read`
* PR validation jobs → maybe `pull-requests: read`
* Labeling or automation bots → `pull-requests: write`
* Deployment jobs → may require `deployments: write`

Never grant broad permissions “just in case.”

---

# 📌 Mental Model

Think of `GITHUB_TOKEN` as:

> A scoped service account for your workflow.

Each job can be given a different level of authority.

Just like IAM roles in AWS:

* Job = role
* permissions block = IAM policy

---

# 🧩 Workflow-Level vs Job-Level Permissions

You can define permissions at the workflow level:

```yaml
permissions:
  contents: read
  pull-requests: write
```

Or override them at the job level:

```yaml
jobs:
  my-job:
    permissions:
      pull-requests: read
```

Job-level definitions override workflow-level definitions.

---

# 🧠 Why This Matters in Real CI/CD

Without permission scoping:

* A compromised workflow could push malicious code
* A third-party action could modify PRs
* Automation could accidentally publish packages

With permission scoping:

* You reduce blast radius
* You enforce compliance
* You align with DevSecOps best practices

---

# 🚀 Key Takeaways

* `GITHUB_TOKEN` is automatically injected
* Default access is minimal (read-only for contents & packages)
* Use `permissions:` to control API access
* Read vs write determines allowed operations
* GitHub CLI uses `GH_TOKEN` environment variable
* Always apply least privilege
