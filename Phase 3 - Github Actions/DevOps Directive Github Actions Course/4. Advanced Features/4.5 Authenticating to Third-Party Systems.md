# DevOps Lock‑In Phase 3

## Module 4.5 – Authenticating to Third‑Party Systems

📅 Date: 18/02/2026

---

## 🎯 Why This Matters

Most real CI/CD pipelines must interact with external systems:

* Cloud providers (AWS, GCP, Azure)
* Container registries
* Artifact repositories
* SaaS platforms (Datadog, Slack, etc.)

That means your workflow needs a secure way to authenticate.

There are **two primary authentication models** in GitHub Actions:

1. **Static Credentials (Long‑Lived Secrets)**
2. **OIDC Federation (Short‑Lived Tokens)** ← ✅ Preferred

---

# 1️⃣ Static Credentials (Legacy / Less Secure)

### 🔹 What It Is

You create long‑lived credentials (like API keys or AWS access keys) and store them in GitHub Secrets.

Example with AWS:

```yaml
jobs:
  auth-to-aws-static:
    runs-on: ubuntu-24.04
    steps:
      - name: Configure AWS Credentials using static key
        uses: aws-actions/configure-aws-credentials@7474bc4690e29a8392af63c5b98e7449536d5c3a
        with:
          aws-region: us-east-2
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
```

### 🔹 How It Works

1. You create an IAM user.
2. Generate access key + secret key.
3. Store them as GitHub repository secrets.
4. Pass them into the AWS action.

### ❌ Why This Is Risky

* Keys are long‑lived.
* If leaked → attacker can use them until revoked.
* Requires manual rotation.
* Broader blast radius.

This approach works everywhere but is not ideal for production.

---

# 2️⃣ OIDC Federation (Modern & Secure)

### 🔹 What It Is

GitHub dynamically mints a **short‑lived JWT token** at runtime.
The cloud provider exchanges that token for temporary credentials.

No secrets stored in GitHub.
No long‑lived keys.

### 🔹 Required Permission

You MUST enable:

```yaml
permissions:
  id-token: write
```

Without this, GitHub cannot request the OIDC JWT.

---

## ✅ AWS OIDC Example

```yaml
jobs:
  auth-to-aws-oidc:
    runs-on: ubuntu-24.04
    permissions:
      id-token: write
    steps:
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@7474bc4690e29a8392af63c5b98e7449536d5c3a
        with:
          aws-region: us-east-2
          role-to-assume: arn:aws:iam::917774925227:role/github-actions-role
```

---

## 🧠 What Happens Behind the Scenes

1. GitHub runner requests an OIDC token.
2. GitHub generates a short‑lived JWT.
3. AWS validates the JWT against its configured OIDC provider.
4. AWS issues temporary role credentials.
5. Workflow runs using those temporary credentials.

When the job finishes → credentials expire automatically.

---

## 🔐 AWS Setup Overview (Conceptual)

To enable OIDC you must:

1. Register GitHub as an OIDC provider in AWS IAM.

   * Provider URL: [https://token.actions.githubusercontent.com](https://token.actions.githubusercontent.com)
   * Audience: sts.amazonaws.com

2. Create an IAM Role.

3. Add a **Trust Policy** that:

   * Allows the GitHub OIDC provider
   * Restricts access to your specific repo/branch

4. Use that role ARN inside your workflow.

# 🔎 Static vs OIDC Comparison

| Feature                 | Static Keys | OIDC        |
| ----------------------- | ----------- | ----------- |
| Credential lifetime     | Long-lived  | Short-lived |
| Secret stored in GitHub | Yes         | No          |
| Rotation required       | Manual      | No          |
| Blast radius            | High        | Minimal     |
| Recommended for prod?   | ❌ No        | ✅ Yes       |

---

# 🧠 Key Mental Model

Static credentials = “Store a password in GitHub.”

OIDC = “Prove identity dynamically and receive temporary access.”

OIDC is identity‑based authentication.
Static keys are secret‑based authentication.

---

# 🏗 Production Best Practice

✅ Always prefer OIDC when supported.

Use static secrets only when:

* The third‑party system does not support OIDC
* You're prototyping
* You're integrating legacy systems

---

# 🔑 Important Takeaways

* GitHub provides built‑in OIDC support.
* You must grant `id-token: write` permission.
* OIDC eliminates secret management overhead.
* AWS, Azure, and GCP all support OIDC.
* This is how modern secure CI/CD pipelines authenticate.
