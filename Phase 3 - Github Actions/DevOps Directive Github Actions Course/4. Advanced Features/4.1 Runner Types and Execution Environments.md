# 🧠 What Is a Runner?

Every GitHub Actions job must declare:

```yaml
runs-on: <runner-type>
```

A **runner** is the machine (virtual or physical) that executes your workflow steps.

When you specify `runs-on`, you are choosing:

* The OS image
* The hardware architecture
* The available compute resources
* The pre-installed tooling
* The infrastructure provider

Think of it as choosing which computer runs your CI pipeline.

---

# 🔑 Core Mental Model

A workflow is just instructions.
A runner is the computer that executes those instructions.

No runner → No execution.

---

# 🏗️ Three Categories of Runner Types

![](Images\runner-types.png)


GitHub Actions supports three broad runner categories:

---

## 1️⃣ GitHub-Hosted Runners

These are managed entirely by GitHub.

Examples:

```yaml
runs-on: ubuntu-24.04
runs-on: windows-2022
runs-on: macos-14
```

Characteristics:

* Turnkey
* Automatically provisioned
* Clean environment per job
* No infrastructure to manage
* Good default choice

Best for:

* Open source projects
* Simpler CI/CD
* Quick setup

Each job gets a fresh VM.

---

## 2️⃣ Third-Party Hosted Runners

These are provided by external companies.

Example shown in course:

```yaml
runs-on: namespace-profile-default
```

Why use them?

* Faster compute
* Better caching
* Lower cost per performance
* Improved observability
* Multi-architecture container builds

Benefits highlighted:

* Higher benchmark performance
* Roughly half the cost (compared to GitHub-hosted x64 in demo)
* Better developer experience

Additional features shown:

* Execution timing insights
* CPU / memory / network / storage metrics
* Historical performance tracking
* Logs at runner level

This improves visibility into CI behavior.

---

## 3️⃣ Self-Hosted Runners

You operate the compute yourself.

Options include:

* Installing runner agent on your own server
* Running inside Kubernetes using Actions Runner Controller (ARC)
* Provisioning ephemeral EC2 instances via tools like RunsOn

Benefits:

* Full control
* Private network execution
* Data remains in your VPC
* Potential cost optimization

Tradeoff:

* You must manage the infrastructure

---

# 🧱 What Does `runs-on` Actually Control?

When you specify a runner, you control:

* Virtual machine image
* OS version
* CPU cores
* RAM
* Base dependencies
* Architecture (x64 vs ARM64)

Example runner context usage:

```yaml
echo "Hello from ${{ runner.os }}-${{ runner.arch }}"
echo "Runner name: ${{ runner.name }}"
```

Important runner context fields:

* `${{ runner.os }}`
* `${{ runner.arch }}`
* `${{ runner.name }}`

This allows workflows to dynamically inspect execution environment.

---

# 🐳 Running Inside Containers

You can combine:

```yaml
runs-on: ubuntu-24.04
container:
  image: alpine:3.20
```

What this means:

* Job runs on Ubuntu VM
* Steps execute inside Alpine container

Why use this?

* Add custom dependencies
* Control tool versions
* Ensure reproducible environments

Important distinction:

The VM still exists.
The container runs on top of it.

---

# 🏷️ Labels and Custom Profiles

Runners can be assigned labels or grouped.

This allows:

* Controlling which jobs run on which hardware
* Selecting high-memory runners
* Selecting ARM64 vs x64
* Custom pre-installed dependency images

Example patterns:

```yaml
runs-on: namespace-profile-default
runs-on: namespace-profile-default-arm64
runs-on: my-self-hosted-runner
```

# 📊 Performance & Cost Considerations

![](Images\runner-benchmark.png)

Reasons to choose third-party or self-hosted:

* Faster builds
* Reduced CI bill
* Better caching
* Custom machine sizes
* Better observability

GitHub-hosted:

* Convenient
* Reliable
* Slightly more expensive at scale

Third-party:

* High performance
* Lower cost
* Better metrics

Self-hosted:

* Full control
* Potential cost optimization
* Infrastructure overhead

---

# 🔐 Security Implications

GitHub-hosted:

* Isolated per job
* Ephemeral

Self-hosted:

* Persistent environment
* Must secure properly
* Potential secret leakage risk if misconfigured

Third-party:

* External compute provider
* Trust boundary changes

Runner choice impacts security posture.

---

# 🧠 Conceptual Summary

A runner is the execution engine of GitHub Actions.

Choosing a runner determines:

* Where your code executes
* How fast it runs
* How much it costs
* What dependencies are available
* What architecture you build for

You can:

* Use GitHub-managed VMs
* Use third-party performance-optimized runners
* Operate your own infrastructure
* Layer container images on top

This is the first step toward treating CI/CD as infrastructure architecture rather than just YAML.

# 📌 Key Takeaways

* `runs-on` determines execution environment
* Three runner categories: GitHub-hosted, third-party, self-hosted
* Containers can be layered onto runners
* Architecture matters (x64 vs ARM64)
* Runner choice impacts performance and cost
* Runner context provides runtime metadata

Runner selection is not cosmetic — it is architectural.
