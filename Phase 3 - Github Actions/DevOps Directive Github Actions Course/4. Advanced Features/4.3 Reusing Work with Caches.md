# DevOps Lock‑In — Phase 3

## 4.3 Reusing Work with Caches

**Date:** 16/02/2026

---

## 1️⃣ Why Caching Exists

GitHub Actions runners are **ephemeral**.

That means:

* A job starts with a fresh virtual machine
* Everything installed/generated during the job is destroyed at the end

So if your job:

* Installs dependencies
* Downloads toolchains
* Builds language runtimes

You must either:

* Do it every single run ❌ (slow)
* Or cache it ✅ (fast)

Caching is for **speed optimization**, not long‑term storage.

---

## 2️⃣ Artifacts vs Cache (Important Difference)

| Artifacts                           | Cache                          |
| ----------------------------------- | ------------------------------ |
| Persist outputs for humans/download | Persist dependencies for speed |
| Visible in UI                       | Invisible performance layer    |
| Long-lived                          | Optimized for reuse            |
| Used across jobs                    | Used across workflow runs      |

Artifacts = "Save this result"

Cache = "Don’t redo this work again"

## 3️⃣ GitHub Official Cache (actions/cache)

GitHub provides:

```
actions/cache
```

### How it works

1. Try to restore cache using a key
2. If cache exists → skip work (cache hit)
3. If not → do work + save cache (cache miss)

### Storage details

* Stored in Azure object storage
* 10GB per repository limit
* Old caches are evicted automatically

---

## 4️⃣ Basic Cache Example

### Step 1 – Try restoring cache

```yaml
- name: Restore cache
  id: demo-cache
  uses: actions/cache@<commit-sha>
  with:
    path: demo-cache
    key: demo-cache-v1
```

### Step 2 – Only generate content if miss

```yaml
if: steps.demo-cache.outputs.cache-hit != 'true'
```

### Step 3 – Save cache if it was a miss

This prevents overwriting a valid cache unnecessarily.

---

## 5️⃣ What Should You Cache?

Typically:

* node_modules
* ~/.m2 (Maven)
* ~/.gradle
* ~/.cache/pip
* Go module cache
* Toolchains

Anything expensive to download/install repeatedly.

---

## 6️⃣ Language‑Aware Caching (Better Approach)

![](Images\cache-example.png)

Instead of manually configuring cache paths, many setup actions support built‑in caching.

Example: Node.js

```yaml
- uses: actions/setup-node@<commit-sha>
  with:
    node-version: 20
    cache: npm
    cache-dependency-path: package-lock.json
```

What happens internally:

* Hash of lockfile becomes cache key
* If lockfile unchanged → instant dependency restore
* If lockfile changed → new cache generated

This is deterministic and clean.

---

## 7️⃣ Cache Key Philosophy

A cache key determines whether you get a hit or miss.

Good cache keys are based on:

* Lock files
* Dependency versions
* OS + architecture

Bad cache keys:

* Static keys that never change
* Overly broad keys

If key never changes → stale cache risk.
If key changes too often → no cache benefit.

---

## 8️⃣ Namespace Cache Volumes (Different Model)

![](Images\namespace-cache-volumes.png)

GitHub Cache:

* Upload to object storage
* Download on restore
* Deterministic via key

Namespace Cache Volume:

* Snapshots entire volume
* Mounts it directly on next run
* No upload/download cycle
* Much faster for large datasets

Tradeoff:

* Slightly less deterministic
* Much faster in practice

Especially useful for:

* Huge dependency trees
* Large build systems
* Thousands of small files

---

## 9️⃣ Performance Insight

When cache HIT:

Namespace volume: ~3–4 sec
GitHub cache: 12–28 sec

When cache MISS:
Both pay initial cost.

So caching is about:

* Paying once
* Benefiting repeatedly

---

## 🔟 Mental Model

Runner lifecycle:

Fresh VM → Install deps → Build → Destroy VM

With cache:

Fresh VM → Restore deps instantly → Build → Destroy VM

Cache is a **performance multiplier**, not storage.

---

## 🧠 Core Understanding Locked

* Runners are ephemeral
* Cache avoids repeated installation work
* GitHub cache uses object storage (10GB limit)
* Cache hit/miss controlled via key
* Setup actions support intelligent caching
* Namespace cache volumes trade determinism for speed
