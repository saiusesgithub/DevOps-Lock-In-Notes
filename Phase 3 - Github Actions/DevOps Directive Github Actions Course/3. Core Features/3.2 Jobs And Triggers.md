# 🧠 Part 1 — Coordinating Multiple Jobs

## Default Behavior: Parallel Execution

When a workflow contains multiple jobs:

* All jobs start **in parallel**
* As soon as the triggering event occurs
* If there are no dependencies defined

Example mental model:

```
Event
  ↓
Job-1   Job-2   Job-3
  (all start immediately)
```

Parallelism is the default optimization.

---

# 🧠 Directed Acyclic Graph (DAG)

GitHub Actions workflows form a:

> **Directed Acyclic Graph (DAG)**

### Directed

There is a direction of execution flow.

### Acyclic

No loops allowed.

You cannot create circular dependencies like:

```
job-a needs job-b
job-b needs job-a ❌
```

That would create a cycle and is invalid.

---

# 🧩 Creating Dependencies with `needs:`

The `needs:` keyword defines explicit job dependencies.

Example:

```yaml
jobs:
  job-1:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "A job consists of"
      - run: echo "one or more steps"

  job-2:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Multiple jobs can run in parallel"

  job-3:
    runs-on: ubuntu-24.04
    needs:
      - job-1
      - job-2
    steps:
      - run: echo "They can depend on one another"

  job-4:
    runs-on: ubuntu-24.04
    needs:
      - job-2
      - job-3
    steps:
      - run: echo "...to form a DAG"
```

---

# 🧠 Execution Flow of This DAG

Step-by-step execution:

1. `job-1` and `job-2` start in parallel
2. After both succeed → `job-3` runs
3. After `job-2` and `job-3` succeed → `job-4` runs

# 🧠 Why This Matters

This enables:

* Gating deployments on test success
* Waiting for builds before packaging
* Coordinating multi-environment rollouts
* Parallel test execution followed by aggregation

Real-world example:

Build → Test → Deploy

Where deploy only runs if build and test succeed.

---

# 🧠 Critical Isolation Rule (Reinforced)

Even with `needs:`:

* Jobs still run in separate environments
* They do not share filesystem or memory

To pass data between jobs, you must use:

* Artifacts
* Job outputs
* Caching

This will be covered later.

# 🧠 Part 2 — Controlling When Workflows Run

Events determine when a workflow executes.

GitHub supports dozens of events.

Most commonly used:

* `push`
* `pull_request`
* `workflow_dispatch`
* `schedule`

![Images\types-of-events.png](Images\types-of-events.png)

![Images\types-of-triggers.png](Images\types-of-triggers.png)

---

# 🧩 Example Trigger Configuration

```yaml
on:
  push:
    branches:
      - "example-branch/*"

  pull_request:
    paths:
      - "03-core-features/filters/*.md"
      - "!03-core-features/filters/*.txt"

  schedule:
    - cron: "0 0 * * *"

  workflow_dispatch:
```

---

# 🧠 Push Event with Branch Filtering

```yaml
push:
  branches:
    - "example-branch/*"
```

This means:

Workflow only runs when:

* A push occurs
* To a branch matching that glob pattern

Glob patterns are supported.

If branch does not match → workflow does not trigger.

---

# 🧠 Pull Request Event with Path Filters

```yaml
pull_request:
  paths:
    - "03-core-features/filters/*.md"
    - "!03-core-features/filters/*.txt"
```

### Path Filtering Rules

Include patterns trigger execution.

Exclude patterns (with `!`) prevent execution.

---

## Example Scenario

If PR modifies:

* `.md` file → workflow runs
* `.txt` file only → workflow does NOT run

This avoids unnecessary CI execution.

---

# 🧠 Why Path Filters Matter (Monorepo Use Case)

In monorepos:

Multiple services live in same repository.

Without path filtering:

Every change triggers every workflow.

This wastes:

* Compute
* Time
* CI minutes

Path filtering enables targeted execution.

---

# 🧩 Schedule Event (Cron)

```yaml
schedule:
  - cron: "0 0 * * *"
```

Cron format:

```
minute hour day month weekday
```

`0 0 * * *` = Midnight UTC daily

Scheduled workflows:

* Run even if no commits occur
* Useful for nightly builds
* Useful for dependency updates
* Useful for health checks

---

# 🧩 Manual Trigger — workflow_dispatch

```yaml
workflow_dispatch:
```

Enables:

“Run workflow” button in UI.

Also runnable via GitHub CLI.

Common use cases:

* Emergency fixes
* Demos
* Debugging
* One-off builds

# 🧠 Inspecting Event Metadata

Every workflow run includes an event payload.

Stored at:

```
$GITHUB_EVENT_PATH
```

This file contains:

* Pull request number
* Branch name
* Modified files
* Actor
* Commit SHA
* Repository metadata

Example debugging step:

```yaml
- run: cat $GITHUB_EVENT_PATH
```

This prints full JSON payload.

Extremely useful for debugging trigger behavior.

# 🧠 Branch Pattern Demonstration

If push matches:

```
example-branch/*
```

Workflow runs.

If push does NOT match pattern:

Workflow does NOT run.

This provides strict control.

---

# 🧠 Combined Mental Model

Event filtering occurs BEFORE workflow execution.

If filters do not match:

Workflow never starts.

This saves compute and CI minutes.
