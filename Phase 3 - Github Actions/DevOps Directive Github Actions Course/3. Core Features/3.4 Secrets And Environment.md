# 🧠 Why Secrets & Variables Exist

Hardcoding credentials inside YAML is dangerous.

Instead of this:

```yaml
DATABASE_PASSWORD: super-secret-password
```

GitHub provides a secure storage mechanism so:

* Sensitive data is encrypted
* Access is controlled
* Values are masked in logs
* Configuration is separated from code

---

# 🔐 Secrets vs Variables

| Feature         | Secrets                      | Variables                          |
| --------------- | ---------------------------- | ---------------------------------- |
| Sensitive data? | ✅ Yes                        | ❌ No (should not be sensitive)     |
| Visible in UI?  | ❌ Cannot read after creation | ✅ Can view & edit                  |
| Masked in logs? | ✅ Yes (*** shown)            | ❌ No                               |
| Use case        | DB passwords, API keys       | Flags, config values, region names |

---

# 🏗️ Storage Levels

Secrets and variables can be defined at:

## 1️⃣ Organization Level

* Shared across multiple repositories
* Good for shared infrastructure credentials

## 2️⃣ Repository Level

* Scoped to a single repository
* Shared across all workflows

## 3️⃣ Environment Level

* Scoped to specific environment (e.g., staging, production)
* Used for deployment separation
* Can enforce approvals and protection rules

Example:

| Environment | DB_PASSWORD  |
| ----------- | ------------ |
| staging     | staging-pass |
| production  | prod-pass    |

Same key name. Different values.

# 🧩 Using Environments in Jobs

Specify environment at job level:

```yaml
jobs:
  deploy:
    runs-on: ubuntu-24.04
    environment: production
```

This tells GitHub:

* Use production-scoped secrets
* Use production-scoped variables
* Apply environment protection rules

---

# 🧪 Referencing Secrets & Variables

Inside YAML expressions:

```yaml
${{ secrets.MY_SECRET }}
${{ vars.MY_VARIABLE }}
```

Typically assign to env so shell can use them:

```yaml
env:
  API_KEY: ${{ secrets.API_KEY }}
```

Then inside shell:

```bash
$API_KEY
```

---

# 🔎 Log Masking Behavior

When printing a secret:

```bash
echo "$MY_SECRET"
```

GitHub shows:

```
***
```

This prevents accidental leakage in logs.

Variables are printed normally.

---

# 🧠 Example Behavior (Staging vs Production)

Two jobs:

```yaml
staging-environment:
  environment: staging

production-environment:
  environment: production
```

Repository-level variable:

* Same in both jobs

Environment-level variable:

* Different value depending on environment

Result:

| Value Type           | Staging Job    | Production Job   |
| -------------------- | -------------- | ---------------- |
| Repo variable        | Same           | Same             |
| Environment variable | Staging value  | Production value |
| Secrets              | Masked in both | Masked in both   |

---

# 🧠 Important Security Insight

Secrets:

* Cannot be retrieved via API
* Cannot be read back once stored
* Only injected at runtime

This ensures:

> Your CI system does not become your weakest security link.

# 🧩 Contexts in GitHub Actions

You access dynamic runtime data using:

```yaml
${{ ... }}
```

This syntax allows access to structured objects called **contexts**.

---

![](Images\contexts.png)

# 📦 Common Contexts

## 🔹 secrets

User-managed sensitive values

```yaml
${{ secrets.DB_PASSWORD }}
```

## 🔹 vars

User-managed non-sensitive configuration

```yaml
${{ vars.APP_REGION }}
```

## 🔹 needs

Outputs from previous jobs

```yaml
${{ needs.build.outputs.image_tag }}
```

## 🔹 steps

Outputs from previous steps

```yaml
${{ steps.generate.outputs.foo }}
```

## 🔹 github

Metadata about:

* Repository
* Branch
* Commit SHA
* Actor
* Event type

Example:

```yaml
${{ github.ref }}
${{ github.actor }}
```

## 🔹 env

Environment variables available in current scope

```yaml
${{ env.MY_VAR }}
```

## 🔹 runner

Information about current runner

## 🔹 job

Information about current job

## 🔹 matrix (advanced)

Used when running multiple parallel job variants

## 🔹 inputs

Used for workflow_dispatch inputs

---

# 🧠 Expressions & Logic

Contexts allow logic in workflows:

```yaml
if: ${{ github.ref == 'refs/heads/main' }}
```

You can:

* Compare values
* Build dynamic strings
* Conditionally execute steps

This turns YAML into a programmable configuration.
