# 🧠 Terminology & Concept Hierarchy

GitHub Actions uses specific terminology. Understanding the hierarchy is critical.

![Images\workflow-architecture.png](Images\workflow-architecture.png)

## 1️⃣ GitHub Event

An event is something that happens in GitHub.

Examples:

* `push`
* `pull_request`
* `workflow_dispatch`
* `release`
* `issue`

Events are exposed via the GitHub API.

Events **trigger workflows**.

---

## 2️⃣ Workflow

A workflow is what other platforms call a pipeline.

It is defined in:

```
.github/workflows/<name>.yml
```

A workflow contains:

* A name
* One or more triggers (`on:`)
* One or more jobs

The entire YAML file represents a workflow.

---

## 3️⃣ Job

A job is a unit of work.

Each job:

* Runs on a runner
* Executes independently
* Has one or more steps

Important property:

Jobs run on **separate compute environments**.

That means:

No shared filesystem.
No shared environment variables.
No shared memory.

---

## 4️⃣ Step

Steps exist inside jobs.

Steps:

* Run sequentially
* Share the same environment within that job

Between steps → same environment

Between jobs → different environment

This distinction is critical for data passing.

---

## 5️⃣ Runner

Runner = The compute environment that executes jobs.

Examples of GitHub-hosted runners:

* `ubuntu-24.04`
* `windows-latest`
* `macos-latest`

You specify runner using:

```
runs-on: ubuntu-24.04
```

Runner determines:

* OS
* Installed tools
* Execution environment

# 🧩 Minimal Workflow Example

![Images\hello-world-workflow.png](Images\hello-world-workflow.png)

```yaml
name: Hello World

on:
  workflow_dispatch:

jobs:
  say-hello-inline-bash:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Hello from an inline bash script in a GitHub Action Workflow!"
```

---

## Breakdown

### name

Human-readable identifier for workflow.

---

### on:

Specifies trigger.

Here:

```
workflow_dispatch
```

This allows manual execution via GitHub UI.

---

### jobs:

Defines job list.

Each job is a key under `jobs`.

---

### runs-on:

Specifies runner type.

Here:

GitHub-hosted Ubuntu 24.04 machine.

---

### steps:

Defines ordered step list.

Steps execute sequentially.

---

### run:

Executes inline shell command.

Default shell on Ubuntu = bash.

# 🧠 Execution Behavior in GitHub UI

When you trigger workflow_dispatch:

1. GitHub queues workflow
2. Assigns runner
3. Executes job
4. Displays logs per step

Queued → Running → Completed

# 🧩 Expanding to Multiple Jobs & Step Types

Second example demonstrates three jobs.

![Images\types-of-steps-workflow.png](Images\types-of-steps-workflow.png)

```yaml
jobs:
  say-hello-inline-bash:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Hello from an inline bash script"

  say-hello-inline-python:
    runs-on: ubuntu-24.04
    steps:
      - run: print("Hello from inline Python")
        shell: python

  say-hello-action:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/hello-world-javascript-action@081a6d193d1dcb38460df1e6927486d748730f9d
        with:
          who-to-greet: "from marketplace action!"
```

---

# 🧠 Step Type 1 — Inline Bash (Default)

Default behavior:

`run:` executes using default shell.

On Ubuntu → bash

Example:

```yaml
- run: echo "Hello"
```

---

# 🧠 Step Type 2 — Override Shell

You can override shell using:

```
shell:
```

Example:

```yaml
- run: print("Hello")
  shell: python
```

Supported shells:

* bash
* sh
* python
* pwsh
* cmd

This enables multi-language scripting inside workflows.

---

# 🧠 Step Type 3 — Reusable Action (`uses:`)

Instead of writing commands inline, you can reuse prebuilt actions.

[https://github.com/actions/hello-world-javascript-action](https://github.com/actions/hello-world-javascript-action)

Example:

```yaml
- uses: actions/hello-world-javascript-action@<commit-sha>
```

This pulls external repository and executes defined action logic.

---

## 🔒 Why Pin to Commit SHA?

You can reference actions by:

* Tag (`@v1`)
* Branch (`@main`)
* Commit SHA (recommended)

Best practice:

Always use full commit SHA.

Reason:

* Prevent supply chain attacks
* Prevent unexpected updates
* Ensure reproducibility

Tags can move.

Commit SHA is immutable.

---

## with:

Inputs passed to action.

Example:

```yaml
with:
  who-to-greet: "Srujan"
```

Actions define required inputs.

# 🧠 Job Execution Model

Important behavior observed:

* Steps inside a job → run sequentially
* Jobs inside workflow → run in parallel (by default)

In expanded example:

Three jobs run simultaneously.

Each has its own runner.

---

# 🧠 Data & Environment Boundaries

Critical rule:

Between steps → same environment

Between jobs → separate environment

Implications:

You cannot rely on:

* Files created in one job being available in another
* Environment variables persisting across jobs

Later sections will cover:

Artifacts
Outputs
Needs dependencies

# 🧠 Key Mental Models

Workflow = Entire YAML file

Job = Independent execution unit

Step = Atomic execution instruction

Runner = Machine executing job

Event = Trigger

# 📌 Why This Structure Exists

This layered structure enables:

* Parallel execution
* Fault isolation
* Flexible orchestration
* Clear dependency modeling

# 📌 Summary of Step Types

Inline Bash → Fast and simple

Inline Alternate Shell → Multi-language scripting

Reusable Action → Modular, reusable automation

# 📌 Reflection

GitHub Actions is structured around isolation and modularity.

Understanding workflow → job → step → runner boundaries is essential.

Everything advanced (caching, artifacts, matrices, dependencies) builds on this foundation.

This section establishes the structural mental model required for designing reliable CI pipelines.
