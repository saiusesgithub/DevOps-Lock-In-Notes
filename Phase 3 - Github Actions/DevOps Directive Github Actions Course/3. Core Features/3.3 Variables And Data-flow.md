# 🎯 Objective of This Section

Understand:

1. How environment variables work in GitHub Actions
2. How variable scope behaves (workflow vs job vs step)
3. How to pass data between steps in the same job
4. How to pass data between different jobs
5. Why environment variables do NOT persist across jobs

This section is about **state management inside CI pipelines**.

---

# 🧠 Core Mental Model (Critical)

> **Steps share a machine. Jobs do not.**

* All steps inside a single job run on the SAME runner
* Different jobs run on DIFFERENT runners (separate compute environments)

Because of this:

* Environment variables persist across steps in the same job
* Environment variables DO NOT persist across jobs
* To pass data between jobs, you must use job outputs

This explains everything in this module.

# Part 1 — Environment Variables & Scope

Environment variables can be defined at three different levels.

## 🔹 1️⃣ Workflow-Level Environment Variables

Defined at the top of the YAML:

```yaml
env:
  WORKFLOW_VAR: I_AM_WORKFLOW_SCOPED
```

### Scope:

* Available to ALL jobs
* Available to ALL steps

This is the widest scope possible inside a workflow.

---

## 🔹 2️⃣ Job-Level Environment Variables

Defined under a specific job:

```yaml
jobs:
  job-1:
    runs-on: ubuntu-24.04
    env:
      JOB_VAR: I_AM_JOB_SCOPED
```

### Scope:

* Available to all steps inside that job
* NOT available in other jobs

---

## 🔹 3️⃣ Step-Level Environment Variables

Defined inside a specific step:

```yaml
- name: Example step
  env:
    STEP_VAR: I_AM_STEP_SCOPED
```

### Scope:

* Only available inside that step
* Disappears once step completes

---

# 📊 Scope Visualization

| Variable Type | Visible In Job 1 Step 1 | Job 1 Step 2 | Job 2 |
| ------------- | ----------------------- | ------------ | ----- |
| Workflow Var  | ✅                       | ✅            | ✅     |
| Job Var       | ✅                       | ✅            | ❌     |
| Step Var      | ✅                       | ❌            | ❌     |

# 🧩 Important Detail: Referencing Variables

Inside shell scripts:

```bash
$VAR_NAME
```

Inside YAML expressions (like if conditions or outputs):

```yaml
${{ env.VAR_NAME }}
```

Two different syntaxes depending on context.

# Part 2 — Passing Data Between Steps (Same Job)

Sometimes values are dynamic.

Example:

* Generated build number
* Calculated checksum
* Image tag
* File path

You must persist them.

![](Images\passing-variables.png)

GitHub provides two special files:

---

## 🔹 $GITHUB_ENV — Persist for Rest of Job

If you append:

```bash
echo "FOO=bar" >> "$GITHUB_ENV"
```

Then:

* `FOO` becomes available in all subsequent steps in that job

Access normally:

```bash
$FOO
```

### Important:

* Only persists inside same job
* Does NOT cross job boundary

---

## 🔹 $GITHUB_OUTPUT — Create Step Outputs

Inside a step with an `id`, you can do:

```bash
echo "foo=bar" >> "$GITHUB_OUTPUT"
```

Then reference it:

```yaml
${{ steps.generate-foo.outputs.foo }}
```

This allows step-to-step data flow.

---

# 🧠 Difference Between GITHUB_ENV and GITHUB_OUTPUT

| Feature    | GITHUB_ENV  | GITHUB_OUTPUT            |
| ---------- | ----------- | ------------------------ |
| Scope      | Rest of job | Explicit output          |
| Access     | $VAR        | steps.<id>.outputs.<key> |
| Cross-job? | ❌ No        | ✅ Yes (if promoted)      |

# Part 3 — Passing Data Between Jobs (Inter-Job)

Because jobs run on separate runners, you MUST explicitly pass data.

### Step 1 — Write Step Output

```bash
echo "foo=bar" >> "$GITHUB_OUTPUT"
```

---

### Step 2 — Promote Step Output to Job Output

```yaml
jobs:
  producer:
    outputs:
      foo: ${{ steps.generate-foo.outputs.foo }}
```

Now the job exposes an output called `foo`.

---

### Step 3 — Declare Dependency Using needs

```yaml
consumer:
  needs: producer
```

This ensures:

* Producer runs first
* Consumer can access its outputs

---

### Step 4 — Reference Output in Downstream Job

```yaml
${{ needs.producer.outputs.foo }}
```

---

# 🔬 Example Behavior Explained

Inside producer job:

```bash
echo "FOO=bar" >> "$GITHUB_ENV"
echo "foo=bar" >> "$GITHUB_OUTPUT"
```

In producer:

* $FOO works
* step output works

In consumer:

* $FOO is UNSET ❌
* job output works ✅

Why?

Because:

> Environment variables do not survive job boundaries.

They are tied to that runner’s environment.

Job outputs are serialized and passed through GitHub’s workflow engine.

---

# 🧠 Execution Timeline

1. Producer runs on Runner A
2. Sets env var (local to Runner A)
3. Sets step output
4. GitHub captures job output
5. Consumer runs on Runner B
6. GitHub injects job output into expression context
7. Env var is gone (Runner A is gone)

---

# 🏗️ Practical Use Cases

Use GITHUB_ENV when:

* Sharing data across steps in same job
* Modifying PATH
* Setting computed flags

Use Job Outputs when:

* Passing artifact names
* Passing image tags
* Passing build numbers
* Gating deployments

---

# ⚠️ Common Mistakes

❌ Expecting environment variables to persist across jobs

❌ Forgetting to assign an id to step when using outputs

❌ Forgetting to define job outputs block

❌ Forgetting to declare `needs`

---

# 🧠 Mental Summary

Environment variables = local to execution environment.

Outputs = explicit data transfer mechanism.

Steps share compute.
Jobs do not.

If you remember only one thing from this section:

> Jobs are isolated. Data must be passed intentionally.
