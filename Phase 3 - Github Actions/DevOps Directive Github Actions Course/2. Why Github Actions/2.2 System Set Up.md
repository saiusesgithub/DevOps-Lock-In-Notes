# 🎯 Objective of This Section

This section establishes the foundational local development environment required to:

* Run GitHub Actions workflows
* Modify workflows safely
* Debug workflows locally
* Ensure reproducibility
* Prevent version mismatch issues

The core goal is to create a **reproducible, isolated, predictable development environment**.

This eliminates "environment drift" — one of the most common sources of CI/CD failures.

---

# 🧠 Core Principle: Reproducible Development Environments

One of the biggest sources of software failures is inconsistent environments.

Example:

Works on developer machine → fails in CI → fails in production

Root cause:

Different tool versions.

Different dependency versions.

Different operating system behaviors.

---

## Solution: Environment Reproducibility

The course enforces reproducibility using:

* Version-pinned tooling
* Isolated shell environments
* Containerized execution

This ensures:

Identical behavior across all machines.

This is foundational for reliable CI/CD.

Repository location:

[https://github.com/sidpalas/devops-directive-github-actions-course](https://github.com/sidpalas/devops-directive-github-actions-course)

---

## Why Fork Instead of Clone Directly?

Forking creates your own copy of the repository under your GitHub account.

This is critical because:

GitHub Actions workflows only run in repositories you own or have permissions for.

Forking gives you:

* Full control over workflows
* Ability to modify workflows
* Ability to execute workflows
* Ability to experiment safely

---

## Mental Model: Ownership enables execution

GitHub Actions executes workflows tied to repository ownership.

Forking transfers ownership to you.

Without ownership, execution permissions may be limited.

# Step 2: Clone the Forked Repository

Clone command:

```
git clone --recurse-submodules https://github.com/<YOUR_USERNAME>/devops-directive-github-actions-course.git
```

Then enter directory:

```
cd devops-directive-github-actions-course
```

---

## Why Use --recurse-submodules?

This repository contains Git submodules.

Submodules are nested repositories referenced by a parent repository.

Purpose:

Provide additional project components.

Example:

Capstone project repository included as submodule.

Without this flag:

Submodules would not be downloaded.

This would break parts of the course.

## Mental Model: Submodules enable modular repository composition

# Step 4: Enter Devbox Shell

Run:

```
devbox shell
```

---

## What happens internally when devbox shell runs

Devbox reads two files:

### devbox.json

Defines required tools.

Example tools may include:

* Git
* Docker
* Node
* CLI tools

---

### devbox.lock

Defines exact versions.

This ensures:

Exact reproducibility.

Without lock file:

Different machines could install different versions.

This could cause failures.

---

## Devbox behavior

When shell starts:

Devbox:

* Checks installed tools
* Installs missing tools
* Pins versions
* Starts isolated shell

This shell environment contains only the course dependencies.

---

## Mental Model: Devbox creates ephemeral isolated environments

Your global system remains untouched.

Devbox environment is isolated.

This prevents conflicts.

# Step 8: Fix YAML File Association Issue

Problem:

GitHub Actions extension overrides YAML association.

Solution:

Add to VS Code settings.json:

```
"files.associations": {
  "**/.github/workflows/*.yml": "yaml",
  "**/.github/workflows/*.yaml": "yaml",
  "**/Taskfile.yml": "yaml"
}
```

---

## Why this is required

Ensures YAML extension handles workflow files.

Enables:

Linting
Validation
Formatting
